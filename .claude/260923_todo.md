# MVLA stage 4 학습 완료 후 할 일

작성 2026-09-23. 전제: `STAGE=4 ./train_xarm7_mvla.sh`와 `./train_xarm7_smolvla.sh`가
같은 8:2 분할(train 234 / val 58)로 50k step까지 돌아간 상태.

순서는 의존성 순이다. **0번을 먼저 보고, 거기서 걸리면 1번 이후는 무의미하다.**

---

## 학습 시작 전 — 이번 런에서 바뀐 것

stage 4 첫 시도가 **step 0에서 OOM으로 죽었다**(137GB/139GB). 헤드를 위해 VLM
prefix를 두 번째로 다시 돌리는 구조였고, 두 activation이 backward까지 살아
있어야 해서 메모리가 거의 두 배였다. stage 1은 헤드가 꺼져 있어 안 드러났다.

**해결**: SmolVLA가 이미 계산하고 버리는 prefix hidden states를 후킹으로 받는다.
추가 연산·메모리 0, 배치 90 유지 → SmolVLA와 동일 조건 비교가 성립한다.

**부수 효과**: 헤드 입력 폭이 **320 → 960**으로 바뀌었다(설계 문서 §4.7 개정).
- 320은 `num_key_value_heads(5) × head_dim(64)`였다. GQA라 KV head가 1/3.
- 카메라 3대와 3배가 우연히 일치하지만 **무관하다.** 세 카메라는 원래부터
  prefix 시퀀스에 나란히 들어가 있었고 pooling 범위도 그대로다.
- 추론 경로(`encode_prefix`)도 hidden states로 통일했다. 학습과 추론이 다른
  특징을 보면 rollout에서 헤드가 무의미해진다.
- 헤드 파라미터 13만 → 39만 (403M 중 0.06%).

검증한 것: step 220까지 에러 0건, 1.15s/step(stage 1과 동일), 보조 손실 4종
모두 wandb 기록, stage 1 경로 무변경, 데이터 대조 테스트 3종 PASS,
**SmolVLA 코드 무수정.**

ls checkpoints/outputs/

## 0. 먼저 — 헤드가 실제로 학습됐는지 확인

학습 중 4000 step마다 wandb에 `val/*`가 찍혔다. 다른 건 보기 전에 이것부터 본다.

| 지표 | 학습 전 기준선 | 판정 |
|---|---|---|
| `val/failure_auc_value` | 0.501 | **0.5 근처면 value 헤드 붕괴.** 0.7+ 면 실패 탐지가 된다 |
| `val/failure_auc_status` | 0.591 | 상동. 다만 val 실패 12건이라 노이즈가 크다 |
| `val/subtask_acc` | 0.183 | 7-class 우연 0.143. 0.7+ 기대 |
| `val/lead_s@0.6` | 0.0 | 양수여야 조기 경보로 쓸 수 있다 |
| `train/loss_subtask` 등 | — | **아예 안 찍혔으면 배치 키 문제 재발.** 260923.md 4번 참고 |

단일 시점이 아니라 step 4000 → 50000 **추세**로 본다. val 실패 런이 12건
(place 7 / flip 4 / move 1)뿐이라 한 점의 AUC는 신뢰구간이 넓다.

**붕괴했다면** rollout으로 넘어가지 말고 원인을 먼저 격리한다:

- `loss_subtask`는 내려가는데 `val/subtask_acc`가 안 오른다 → 과적합.
  234 에피소드에 403M 파라미터다. `subtask_loss_weight` 조정이나 조기 종료.
- `loss_status`가 거의 0으로 붙었다 → always-running 붕괴.
  설계 문서 §4.5가 가중치를 두 번 고친 이유다. `(0.3, 75, 1000)`으로도
  안 되면 터미널 프레임 오버샘플링을 검토.
- 전부 우연 수준 → stage를 2로 내려 subtask 헤드만 켜고 격리.
- 로그에 `MVLA: prefix capture missed` 경고가 있다 → 후킹이 실패해 재계산
  폴백으로 돌았다는 뜻. 학습은 맞지만 메모리를 두 배 쓰므로 원인을 봐야 한다
  (SmolVLA 내부 구조가 바뀌었을 가능성).

## 1. 두 런 비교 — 학습 손실로는 비교하지 말 것

⚠️ **MVLA와 SmolVLA의 `train/loss`를 직접 비교하면 안 된다.** 두 가지 이유:

1. MVLA는 보조 손실이 더해져 숫자의 의미가 다르다.
2. 더 중요한 건, **SmolVLA가 부당하게 유리하다.** SmolVLA는 원문 프롬프트
   ("flip it upside down...")를 받아 답을 알고 시작하고(설계 문서 §2.4의
   99.7% 누수), MVLA stage 4는 중립 프롬프트로 이미지에서 읽어내야 한다.
   학습 손실만 보면 베이스라인이 이긴다. MVLA가 이기는 지점은 프롬프트가
   답을 안 알려주는 실제 상황이다.

비교는 `val/*` 헤드 지표와 3번의 rollout으로 한다.

## 2. 평가 도구 보강 (rollout 전에 필요)

### 2.1 `eval_heads.py`를 체크포인트에 직접 돌리는 진입점

현재는 학습 루프 안에서만 호출된다. 학습이 끝난 뒤 특정 체크포인트를
평가하려면 CLI가 필요하다. `recognizer/train.py`가 참고할 만한 형태다.

```
python -m lerobot.policies.mvla.eval_heads_cli \
    --checkpoint checkpoints/outputs/<job>/checkpoints/050000 \
    --split split_260923.json
```

⚠️ **헤드 폭이 960인 체크포인트와 320인 체크포인트는 호환되지 않는다.**
stage 1 pair test(`checkpoints/outputs/stage1_pair_test`)는 320 시절 것이라
지금 코드로 로드하면 shape 오류가 난다. stage 1은 헤드가 꺼져 있어 어차피
평가할 대상이 없으므로 문제되지 않지만, 혼동하지 말 것.

한 번에 15분(val 52,695 프레임) 걸린다. 체크포인트 여러 개를 비교할
계획이면 런당 샘플링으로 6배 단축하는 선택지가 있다(리드타임 정확도는
희생된다 — 시간 해상도가 필요한 지표라서).

### 2.2 subtask 헤드 혼동행렬

`val/subtask_acc` 하나로는 어느 서브태스크가 헷갈리는지 모른다. 런타임에
정책이 자기 프롬프트를 쓰는 구조라(§4.3), 헤드가 틀리면 rollout이
실패해도 원인을 못 짚는다. 특히 `approach_flip` ↔ `approach_pick` 혼동은
flip 판단 실패와 직결된다.

### 2.3 flip 판단 능력 분리 측정

val 58개 중 flip 필요가 24개다. **중립 프롬프트만 주고** 정책이 flip으로
가는지 pick으로 가는지 본다. 이게 MVLA의 핵심 주장이고, rollout보다 싸게
잴 수 있다.

## 3. 실기 rollout — 조건당 50회

설계 문서 §9 Phase 4. **50회로 검출 가능한 격차는 다음과 같다:**

| 베이스라인 성공률 | MVLA가 이만큼은 나와야 p<0.05 |
|---|---|
| 40% | 62% (+22%p) |
| 50% | 72% (+22%p) |
| 60% | 80% (+20%p) |
| 70% | 88% (+18%p) |
| 80% | 96% (+16%p) |

풀 태스크 49.2초 × 100회(양쪽) = 순수 실행 1.4시간. 리셋·라벨링 포함
2~3배. 20회였다면 30~35%p가 필요했으므로 50회는 의미 있는 개선이다.

### 준비물

- **초기 조건 고정 세트 10~20개.** 없으면 50회를 돌려도 분산이 조건 차이인지
  방법 차이인지 모른다. 부품 위치·자세를 사진으로 남겨 재현 가능하게.
- **기록은 이진이 아니라 서브태스크 진행도.** "실패"만 남기면 approach에서
  죽은 것과 place에서 죽은 것이 같아진다. 실패 분석이 불가능해진다.
- **모든 rollout 저장.** 다음 단계 학습 데이터이자 advantage(7단계)의 전제다.
- 안전 장치: 속도·작업공간 제한, 비상 정지.

### 순서

1. 스모크: `pick up`(11.8초) × 20 — 파이프라인이 도는지만 확인
2. 마일스톤: 풀 태스크(49.2초) × 50 × 2조건
3. 실패 유도 시나리오 — flip·place에 실패가 몰린다

### 런타임 통합이 먼저 필요하다

`planner/manager.py`의 `TaskManager`는 이미 완성되어 있다(경계 검증,
리프롬프트, 재시도 상한, 히스테리시스). 없는 것은 **`runtime.py`** —
매니저와 VLA를 잇는 루프다:

- subtask 헤드 예측 → **1청크 지연** 적용 → 프롬프트 재조립
- `read_state()`로 value 폴링(30Hz, denoising 없이)
- ROS2 연결 (`max_data_collect` 노드)

1청크 지연이 안전한 근거는 §2.3에 측정치로 있다(경계에서 동작 불연속
1.25배, 시연자가 멈추지 않음).

## 4. rollout 이후

- **rollout 라벨링** — `max_data_editor`, 인식기가 보조 가능
- **인식기 재검증** — rollout은 분포가 다르다. 플라시보 재실행 필수.
  기권한 케이스가 `unknown_pose` 후보(현재 0건이라 이 클래스가 비어 있다)
- **advantage 구현(stage 7)** — 알고리즘의 핵심. rollout이 전제라 지금은 불가
- **subgoal 구현(stage 5)** — 우선순위 낮음. 생성이 아니라 **검색**으로 시작

## 5. 중간 stage ablation (선택)

stage 4가 잘 나오면 중간은 ablation일 뿐이다(설계 문서 §9). 나쁘게 나왔을
때 원인을 격리하려고 내려간다.

| stage | 켜지는 것 | 이걸로 답하는 질문 |
|---|---|---|
| 2 | subtask 프롬프트 + 헤드 | subtask 조건화만으로 이득이 있나 |
| 3 | + metadata, 중립 프롬프트 | 중립 프롬프트가 성능을 깎지 않나 |

stage 1은 이미 검증됐다 — SmolVLA와 평균 상대오차 0.33%로 일치했다
(파라미터 수까지 403M 동일). 다시 돌릴 이유가 없다.

## 알려진 한계 — 결과 해석 시 기억할 것

| 항목 | 내용 |
|---|---|
| **flip 실패 리드타임** | 구조적으로 음수. 중간에 결함이 안 보여 정체가 누적돼야 안다. 경과시간 입력으로 완화되나 제거 불가. flip 복구는 시간 압박이 없어 실용상 허용 |
| **val 실패 12건** | AUC 신뢰구간이 넓다. 추세로 보고, 단일 수치로 결론내지 말 것 |
| **`place` 실패 라벨 부족** | 시각적으로 학습 가치가 가장 높은데 가장 적다 |
| **정책 고유 실패 모드** | 발산·프리즈는 시연 데이터에 없다. rollout 전까지 미지 |
| **런타임 진동** | 매니저 되먹임 루프. 히스테리시스 구현했으나 실기 미검증 |
| **`value_episode`** | 녹화된 에피소드 길이 기준이라 정책이 더 빠르거나 느리면 의미가 달라진다. 절대 진척도로 해석 금지. 실패 탐지는 `V_subtask` 담당 |
