# MVLA 설계·구현 기록 (2026-09-23)

xarm7 키팅 데이터셋으로 SmolVLA 기반 VLA를 만들면서, pi0.6(RECAP)·pi0.7의
구조를 참고해 상태 인식기·태스크 플래너·value 기반 실패 탐지를 붙인 작업의
전체 기록이다.

이 문서의 목적은 **왜 그렇게 결정했는지**를 남기는 것이다. 대화 과정에서
측정으로 뒤집힌 결정이 여러 번 있었고, 근거 없이 코드만 보면 재발한다.

- 코드: `thirdparty/lerobot/src/lerobot/policies/mvla/`
- 데이터셋: `datasets/lerobot/xarm7_kitting_260923`, Hub `moonjongsul/xarm7-kitting-260923`
- 학습 스크립트: `thirdparty/lerobot/train_xarm7_{mvla,smolvla}.sh`

## 1. 데이터셋

### 1.1 규모

| | |
|---|---|
| 에피소드 / 프레임 | 292 / 284,562 (30fps, 약 158분) |
| 카메라 | `wrist_front`, `wrist_rear`, `env` (640×480) |
| action | 7D `[vx vy vz wx wy wz gripper]` (cartesian velocity) |
| state | 8D `[vx..wz gripper gripper_effort]` |
| 태스크 | 5종 |
| 서브태스크 | 6종, 프레임 100% 커버 |

`observation.state.eef_rot6d`(11D), `eef_quat`(9D)도 함께 저장되어 있다.

### 1.2 서브태스크 런 구조 — 모든 것의 기반

에피소드가 아니라 **런(run)** 이 분석 단위다. 런은 한 에피소드 안에서
`subtask_index`가 연속으로 유지되는 구간, 즉 "한 서브태스크에 대한 한 번의 시도"다.

| subtask | 런 수 | 성공(1.0) | 부분(0<s<1) | **실패(0.0)** |
|---|---|---|---|---|
| `approach_flip` | 166 | 126 | 40 | **0** |
| `flip` | 168 | 114 | 5 | **49** |
| `approach_pick` | 280 | 267 | 13 | **0** |
| `pick` | 278 | 263 | 8 | **7** |
| `move` | 220 | 202 | 17 | 1 |
| `place` | 256 | 218 | 1 | **37** |
| **합계** | **1,368** | | | **94** |

**핵심 발견 1 — `approach_*`는 실패가 0건이다.**
우연이 아니라 의미론적으로 옳다. 접근을 어설프게 하면 그 대가는 이어지는
조작 서브태스크의 실패로 나타나고, 크레딧이 거기 붙는다. 그래서
`approach_*`에는 성공/실패 라벨을 주지 않는다.

**핵심 발견 2 — 실패는 복구로 이어진다.**
94건의 실패 런 중 92건이 다음 런으로 이어지고, 에피소드 중단은 2건뿐이다.

```
실패 후 다음 서브태스크:  approach_pick 48,  approach_flip 44,  (종료) 2
```

예시(ep12):
```
approach_flip(1.0) → flip(0.0, 17.7s) → approach_flip(0.4) → flip(0.0, 0.7s)
→ approach_flip(0.4) → flip(0.0, 2.4s) → approach_flip(1.0) → flip(1.0, 11.9s) ✓
```

즉 **"실패했을 때 어떻게 되돌아가는가"가 데이터에 들어 있다.**
모방학습이 구조적으로 못 배우는 바로 그 부분이며, pi0.6이 비싼 인간 개입
데이터를 수집해서 얻으려는 것이다.

실패 런은 23,105 프레임 = 전체의 8.1%.

**핵심 발견 3 — 에피소드 단위로 보면 실패가 6건뿐이다.**
서브태스크 단위로 보면 94건. **15배 차이.** 이것이 MDP를 서브태스크 단위로
정의한 이유다.

⚠️ **32개 에피소드에 실패한 `place`와 성공한 재시도가 함께 있다.**
에피소드 단위로 집계하면 0과 1을 평균내어 존재하지 않는 라벨이 만들어진다.
모든 평가는 런 단위여야 한다.

### 1.3 변환 과정에서 고친 것

**① `green tray` → `white tray` (라벨 오류)**
메인 프롬프트는 전부 "white tray"인데 세그먼트 프롬프트만 "green tray"였다.
같은 프롬프트 안에 두 색이 동시에 들어가 색상 grounding을 정면으로 망가뜨린다.
원인은 녹색 작업 매트를 트레이로 오기입한 것. 220개 `edits.json`(479곳)과
`meta/subtasks.parquet`을 수정. `editor_config.yaml`에서는 이미 주석 처리되어 있었다.

**② `gripper_effort` 채널 복원**
원본 HDF5에는 있으나 LeRobot 변환본에서 빠져 있었다. 파지 실패·미끄러짐을
잡는 대표 신호이고, 최다 실패인 `flip`에서 특히 필요하다.
`data_convert_lerobot_config.yaml`의 `source`에 추가해 state 7D→8D.

검증: 원본 HDF5와 최대 절대오차 **0.000e+00**, 프레임 수·라벨 모두 기존 260918과 동일.

⚠️ `observation.state`가 7→8D가 되었으므로 **기존 SmolVLA 체크포인트와 호환되지 않는다.**
`smolvla_kit_rot6d_*` 등은 이어서 학습할 수 없다.

`gripper_effort_raw`는 여전히 미포함(정규화본만). 하드웨어 교체 시 재캘리브레이션
없이 비교 가능한 유일한 채널이므로, 진단용으로 필요하면 `metadata:`에 추가.

## 2. 측정으로 확정한 사실들

설계 결정의 근거다. **추측이 아니라 실측값이다.**

### 2.1 실패는 두 종류이고 기전이 다르다

| | **place형** (37건) | **flip형** (49건) |
|---|---|---|
| 성질 | 잘못된 결과 상태 | 미완결 시도(포기) |
| 증상 | 부품이 포켓에 안 앉고 리브에 걸침 | 목표 자세 도달 실패 후 재시도 |
| 이미지에서 | **명백**, 종료 5초 전에도 보임 | 중간엔 **정상으로 보임** |
| 탐지 기전 | 시각적 이상 | **정체(stall)** — 시간 대비 진척 없음 |
| 단일 프레임으로 | 가능 | **원리적으로 불가능** |

ep12의 실패한 flip을 시간순으로 확인한 결과: 5.4초 지점에서 파지 상태가
완전히 정상으로 보인다. 결함이 생기는 게 아니라 "목표 상태에 도달하지 못하고
끝나는" 것이다.

### 2.2 proprioception으로는 리드타임이 0이다

실패/성공 런을 앞에서부터 N초만 잘라 구분 가능한지 측정 (AUC 0.5 = 구분 불가):

| | 앞 1초 | 앞 2초 | 앞 3초 | 런 전체 |
|---|---|---|---|---|
| **flip** (실패49/성공119) | 0.58 | 0.52 | 0.29 | 0.17 |
| **place** (실패37/성공219) | 0.48 | 0.52 | 0.51 | **0.50** |

- **flip**: 런 전체를 봐야 갈라지는데, 이는 "실패한 flip은 짧다"(중앙값 3.7초 vs 12.2초)는
  사후 정보다. 실시간 탐지에 쓸 수 없다.
- **place**: 런 전체를 봐도 **0.50**. 시간 8.33 vs 8.33초, 경로 0.175 vs 0.181,
  회전 이동량 1.059 vs 1.074 — 운동학적으로 **완전히 동일**하다.

→ **state-MLP critic은 여기서 무의미하다. value function은 반드시 이미지 조건부여야 한다.**

### 2.3 서브태스크 경계는 물리적으로 매끄럽다

| | 경계에서 | 세그먼트 내부 | 비율 |
|---|---|---|---|
| 속도 명령 점프 | 0.0181 | 0.0145 | **1.25×** |
| 그리퍼 점프 >0.1 | 0.7% | 0.3% | 2.3× |

속도 프로파일(경계 전후 ±1.5초, 1076개 평균): 경계에서 **멈춤이 없다**
(0.0471 m/s, 전체 평균 0.0459). 시연자가 서브태스크마다 멈칫거렸다면 정책이
그 멈춤을 배워 throughput이 망가지는데, 그 문제가 없다.

청크가 경계를 넘는 비율: `chunk_size=30` → 11.3%, `chunk_size=50` → **19.5%**.

→ 경계는 연속 동작 위의 의미 오버레이다. 청크가 넘어가도 무해하며,
**subtask 헤드를 1청크 지연 적용해도 안전하다.**

### 2.4 프롬프트가 정답을 누설하고 있었다

| | 시작 `approach_flip` | 시작 `approach_pick` |
|---|---|---|
| 프롬프트에 "flip" 있음 | 120 | 1 |
| 프롬프트에 "flip" 없음 | 0 | 113 |

**상관 119/120 = 99.7%.** `Task: "flip the ... then pick it up"`이 이미 답을
알려주므로 **모델이 이미지를 볼 이유가 없다.** 그대로 학습하면 물체 자세
인식 능력이 0인 채로 프롬프트만 읽는 모델이 나온다.

→ 중립 프롬프트를 도입. 상세는 §4.2.

## 3. 상태 인식기

### 3.1 VLM은 이 판정을 못 한다 (실측)

"VLM에 목표 이미지와 현재 이미지를 주고 판단"하는 구조가 가능한지
직접 블라인드 테스트했다. 클래스당 참조 이미지 1쌍 제공, 정답을 모르는
상태로 판정 후 기록 → 채점.

| 테스트 | 정확도 | 무작위 |
|---|---|---|
| **A. flip 필요 여부** (20장, 10/10) | **35%** | 50% |
| **B. place 안착 여부** (16장, 8/8) | **75%** | 50% |

**Test A가 우연보다 나쁜 이유**: 참조 1쌍에서 "좁고 길쭉함 = target,
넓게 퍼짐 = flipped"라는 규칙을 뽑았는데, 이건 뒤집힘이 아니라
**부품의 yaw(수직축 회전)** 였다. 참조 쌍이 우연히 yaw가 달랐고,
그 결과 진짜 라벨과 **역상관**된 특징을 썼다.

정답을 알고 나서 다시 봐도 일관된 규칙이 보이지 않았다. **프롬프트를 잘 쓰면
되는 문제가 아니라, yaw 변화를 뚫고 살아남는 특징을 많은 예시에서 통계적으로
학습해야 찾을 수 있는 문제다.**

신뢰구간: A는 [18%, 57%]로 "우연보다 낫다는 증거 없음"이 정직한 진술.
B는 [51%, 90%].

→ **VLM은 지각 층이 아니라 기호/계획 층에 둔다.**

### 3.2 학습된 분류기는 압도적이다

| | VLM zero-shot | **학습된 선형 프로브** |
|---|---|---|
| flip 필요 여부 | 35% | **94.5%** (AUC 0.991) |
| place 안착 여부 | 75%, recall 0.62 | **95.7%** (AUC 0.966) |

구성: 동결 DINOv2-base + 로지스틱 회귀. 특징 추출 수십 초, 프로브 학습 즉시.

### 3.3 ⚠️ 평가 프로토콜 — 개발 중 실제로 사고가 났다

**첫 측정 98.3%는 가짜였다.**

플라시보 대조(부품이 전혀 없는 좌측 작업대 영역만 사용)에서 **94.9%**가 나왔다.
부품 자세가 아니라 **녹화 세션 단서**를 읽고 있었던 것이다.

교차-세션 분할이 확증:
```
train=task[1,4] → test=task[0,3]:  97.2%   ← 세션 단서가 정렬되어 우연히 맞음
train=task[1,3] → test=task[0,4]:  45.5%   ← 정렬이 깨지자 우연 이하 (AUC 0.488)
```

**랜덤 CV + 고정 크롭만 봤다면 "98% 달성"으로 보고하고 넘어갔을 것이다.**

필수 장치 4가지:

| 규칙 | 없으면 |
|---|---|
| **플라시보 대조** — 대상이 없는 영역으로 같은 실험 | 배경 단서로 98% 찍고 속음 |
| **연속 블록 CV** — 에피소드 번호 = 녹화 순서 ≈ 세션. **섞으면 안 됨** | 랜덤 CV가 세션 누수를 숨김 |
| **배경 마스킹** | 무엇을 보고 맞히는지 통제 불가 |
| **런 단위 집계** | place는 한 에피소드에 실패+재시도 공존(32건) |

> 추가 사고: "5회 반복 평균"을 하면서 블록 순서를 섞었더니 플라시보가
> 0.122 → 0.657로 부풀었다. **연속 블록을 유지하고 블록 개수만 바꿔야 한다.**

`recognizer/train.py`는 플라시보 마진이 0.15 미만이면 **실패로 종료**한다.

### 3.4 Task B 재측정 — 1차는 무효였다

| | 1차 (무효) | **2차 (유효)** |
|---|---|---|
| 프레임 | 런 종료 | **릴리스 +8/+18/+28** |
| 부품 특정 | "가장 큰 검은 덩어리" (이웃 부품과 병합) | **화면 중앙 = 그리퍼 바로 아래** |
| 플라시보 | 좌측 스트립 | 좌상단 구석 |
| **플라시보 AUC** | **0.960** ⚠️ 안 무너짐 | **0.718** ✅ |

원인: 런 종료 시점은 팔이 릴리스 후 **약 3초(89프레임)** 물러난 뒤라 시야가
넓어지고, "플라시보" 영역에 방금 놓은 부품이 들어가 있었다.

절제 실험이 깔끔하게 정렬된다:

| 입력 | AUC |
|---|---|
| 플라시보 (맥락만, 부품 없음) | 0.718 |
| 부품 마스킹 (부품만, 배경 제거) | 0.958 |
| 중앙 크롭 (부품 + 주변 포켓) | **0.983** |

"부품이 포켓에 앉았는가"는 부품과 포켓의 **관계**이므로, 맥락을 조금 포함한
중앙 크롭이 최고인 게 물리적으로 맞다.

### 3.5 백본 — DINOv2보다 나은 것이 없다

7종 비교 (연속 블록 CV 5회 반복 평균 ± 표준편차):

| 모델 | Task A acc / AUC | Task B AUC / AP |
|---|---|---|
| siglip-so400m-384 | **98.7%** / 0.986±0.013 | 0.976±0.003 / 0.836 |
| **dinov2-base** | 98.3% / **0.989**±0.010 | 0.967±0.011 / 0.857 |
| aimv2-large | 98.0% / 0.988±0.008 | 0.949±0.013 / 0.752 |
| clip-vit-large | 96.8% / 0.988±0.006 | **0.981**±0.006 / **0.866** |
| 앙상블 3종 | 98.9% / 0.988 | 0.983±0.003 / 0.864 |

*(dinov2-large, dinov2-registers, siglip2-base는 더 낮아 생략. DINOv3는 게이트로 접근 불가.)*

**표준편차가 ±0.006~0.014다. 0.03 미만 차이는 전부 노이즈다.**

다른 지렛대도 전부 막혀 있다:

| 시도 | 결과 |
|---|---|
| 해상도 224→448 | AUC 0.985 → 0.986 (**변화 없음**) |
| 프로브 LogReg/SVM/MLP/kNN | SVM +0.009 AUC, AP −0.05. MLP·kNN 과적합 |
| 백본 크기 base→large | dinov2-large가 base보다 **더 나쁨** |

→ **한계가 백본이 아니라 데이터에 있다.** Task B AP 신뢰구간 [0.83, 0.98]의
폭은 양성 37개에서 온다. 백본으로 얻는 ±0.01은 그 안에 묻힌다.

### 3.6 SmolVLA 타워 공유 — 측정 후 기각

"VLA와 인식기가 같은 인코더를 공유해 연산을 한 번만" 아이디어를 검증했다.

**결정적 사실 ①: 절감이 없다.**
```
SmolVLA 비전 타워 = SmolVLMVisionTransformer, 86.4M
DINOv2-base                                 = 86.0M   ← 같은 크기
```
인식기는 0.3Hz(서브태스크 경계)로만 돈다. 30Hz VLA 옆에서 측정 자체가 안 되는 수준.

**결정적 사실 ②: KV 공유는 해상도가 안 나온다.**
```
SmolVLA: 512×512, patch 16 → 32×32 = 1024 패치
         pixel shuffle scale_factor=4 → 64 토큰 = 8×8   ← LLM/KV에 들어가는 것
```
| 공유 지점 | 그리드 | 부품이 차지하는 토큰 |
|---|---|---|
| 비전 타워 출력 (pixel shuffle 전) | 32×32 | ≈ 9×9 ✅ |
| **VLM KV 캐시** (후) | 8×8 | **≈ 2×2** ❌ |

**결정적 사실 ③: 공유 ROI의 우위는 실력이 아니라 맥락 흡수다.**

연속 블록 CV (k=4,5,6 평균):

| 구성 | A acc / AUC | B AUC / AP | 플라시보 A / B |
|---|---|---|---|
| **별도 DINOv2-base · 마스킹 크롭** | **97.9%** / 0.980 | 0.974 / 0.890 | **0.096** / 0.719 |
| SmolVLA 타워 · 공유(전체프레임+ROI) | 95.7% / 0.983 | 0.983 / 0.919 | 0.204 / **0.887** |
| SmolVLA 타워 · 크롭 재인코딩 | 94.4% / 0.980 | 0.965 / 0.827 | — |

SmolVLA 타워 **자체는 DINOv2보다 약하다**(같은 크롭으로 0.965 vs 0.974).
공유 ROI로 바꾸면 0.983으로 오르는데, 성능 +0.009 동안 **플라시보가 +0.168** 올랐다.
ViT는 전역 self-attention이라 ROI 안의 토큰도 화면 전체를 흡수한다.

→ **전부 분리.** 유일한 비용은 메모리 +170MB(fp16).

추가로, 자기 평가 헤드는 자기 맹점을 공유한다. place 게이트는 안전 장치이므로
**정책과 독립된 실패 모드**가 존재 이유다.

### 3.7 최종 구성

```
DINOv2-base (86M, 0.3Hz)
  ├─ mat_state      ← wrist_front/rear, 부품 마스킹 크롭
```

## 4. MVLA 정책

### 4.1 구조

SmolVLA를 **상속**한다. 포크가 아니다. flow matching action expert, prefix 구성,
RTC 처리는 SmolVLA 것을 그대로 쓰고, MVLA가 추가하는 것은 prefix pooled read와
그 위의 헤드들이다.

```
prefix (VLM)
  [env][wrist_front][wrist_rear]   (+ subgoal 2뷰, 미구현)
  "Task: {중립}. Subtask: {sub}. Speed: {bin}. Quality: {1-5}.
   Mistake: {t|f}. Advantage: {pos|neg}."
  [state: vx..wz, gripper, gripper_effort, elapsed_subtask]
         ↓ pooled (960D — 4.7 참고, 320D에서 개정)
헤드    subtask(7) / V_subtask(201) / V_episode(201) / status(3)
suffix  action expert → flow matching (기존, 무수정)
```

**stage 1(모든 헤드 off)은 SmolVLA와 정확히 같아야 한다.** 그렇지 않으면
이후 비교가 헤드가 아니라 리팩터를 측정하게 된다. 어댑터가 원본 데이터셋을
그대로 반환하도록 해서 이를 코드로 보장했다.

### 4.2 중립 프롬프트

§2.4의 99.7% 누수를 차단한다. 목표 기준으로 재분류:

```python
NEUTRAL_PROMPTS = {
    "kit":   "kit the black plastic object into the white tray",
    "pick":  "pick up the black plastic object",
    "place": "kit the black plastic object into the white tray",
}
```

핵심은 **방법이 아니라 목표로 분류**하는 것이다. "grasp it, flip it, then pick
it up"과 "pick up the object"는 목표가 같고(물체가 손에 들림), 뒤집기가 먼저
필요한지만 다르다. 그게 바로 이미지에서 읽어야 할 사실이므로 같은 프롬프트에 매핑한다.

**측정 방식이 개정되었다** (초기 48.7% → 현재 61.6%). 현재는 전체 292개
에피소드에 대해 "문장별 최선 추측"의 정확도로 잰다.

- 하한이 0.5가 아니라 **0.582**: 122/292가 flip 필요이므로 "전부 flip 불필요"만
  해도 그만큼 맞는다.
- 중립 프롬프트는 **0.616**. 잔여분은 어휘가 아니라 구조적인 것 —
  두 목표의 flip 필요 비율이 실제로 다르다(kit 36.8%, pick 56.9%).
  이를 없애려면 플래너가 쓰는 목표 구분까지 없애야 한다.
- 임계값 **0.62**. 기존 프롬프트는 0.997이므로 방법이 어휘로 새면 크게 실패한다.

⚠️ 학습 시 50% 확률로 중립/원문을 섞고, **추론 시에는 항상 중립**을 쓴다.

### 4.3 metadata — 텍스트여야 하는 이유

pi0.7은 metadata를 **plain text**로 넣는다. 학습 임베딩 토큰이 아니다.
이유가 명확하다: 각 필드를 독립적으로 dropout해야 **추론 시 CFG**를 걸 수 있다.
조건화 토큰에 대응하는 무조건부가 없으면 guidance가 불가능하다.

| 항목 | 학습 | 추론 | dropout |
|---|---|---|---|
| Subtask | GT | aux head, **1청크 지연** | 30% (subgoal 있을 때) |
| Quality | `observation.score×5` | **5 고정** | 5% |
| Speed | `length` 500프레임 bin | 태스크별 15th 퍼센타일 | 5% |
| Mistake | `subtask_score < 0.5` | **false 고정** | 5% |
| Advantage | value 기반 (미구현) | positive 고정 | 10% |
| metadata 전체 | — | — | 15% |

**추론 값은 평균이 아니라 최선값이다.** 그래야 suboptimal 시연으로 학습하는 것이
오히려 도움이 된다 — metadata가 어느 것이 나빴는지 알려주기 때문이다.

실측 dropout 확률 (3000회): 중립 0.49 / Subtask 0.79 / Quality 0.80 / Mistake 0.80.
설정값과 일치.

### 4.4 value 헤드는 distributional이어야 한다

§2.2에서 봤듯 **런 초반에는 성공과 실패가 관측상 구분되지 않는다.**
이때 올바른 예측은 "성공값"도 "실패값"도 아니라 **두 봉우리를 가진 분포**다.

- 201-bin cross-entropy는 이를 표현할 수 있다.
- 스칼라 회귀는 중간값으로 뭉갠다.
- **분포가 갈라지는 시점 = 실패가 관측 가능해지는 시점**이므로, 분산 자체가
  "지금 위험하다"는 신호다. `spread()` 메서드로 노출.

RECAP 보상 정의를 **서브태스크 단위**로 적용:
```
r_t = 0        (서브태스크 성공 종료)
    = -C_fail  (서브태스크 실패 종료)   ← 94건 실재
    = -1       (그 외)
```
→ value = "성공까지 남은 스텝의 음수", (-1, 0] 정규화. 실패는 -1에 고정.

정규화 기준은 서브태스크별 **성공 런 길이의 95 퍼센타일**. 느린 서브태스크가
길다는 이유만으로 실패 취급되지 않도록.

### 4.5 ⚠️ status 헤드 — 가중치를 두 번 고쳤다

터미널 프레임은 런의 마지막 하나뿐이므로:

| 클래스 | 프레임 | 비율 |
|---|---|---|
| running | 283,194 | **99.52%** |
| success | 1,274 | 0.45% |
| failure | **94** | **0.033%** |

**"항상 running"이라 답해도 정확도 99.5%다.**

초기값 `(1.0, 5.0, 15.0)`은 완전히 부족했다:

| | 수정 전 | 수정 후 `(0.3, 75.0, 1000.0)` |
|---|---|---|
| always-running 가중손실 | **0.27** (붕괴) | **6.66** |
| 기여도 running/success/failure | 97.3 / 2.2 / 0.5% | **30.9 / 34.8 / 34.2%** |

빈도 역수를 그대로 쓴다. 완화하지 않은 이유는 위 표의 0.27 때문이다.

### 4.6 경과시간 입력 — SmolVLA의 구멍을 메운다

flip형 정체를 감지하려면 시간 정보가 필요한데 **SmolVLA는 현재 프레임 하나만 본다.**
"공중에 부품을 쥔 프레임"은 3초 지점과 15초 지점이 **완전히 동일하다.**
pi0.7은 MEM history encoder로 6프레임을 넣지만 SmolVLA에는 없다.

해법: 현재 서브태스크 경과시간을 state에 1채널 추가. 추론 시에도 정직하게 알 수
있는 값이므로(subtask head가 전환 시점을 안다) **누수가 아니다.**

⚠️ **구현상 함정**: 데이터셋에서 `observation.state`에 직접 붙이면 안 된다.
정규화 통계가 8채널 기준이라 9번째에서 broadcast가 깨진다.
별도 키로 넘기고 `MVLAPolicy.prepare_state`가 **정규화 이후** 패딩 슬롯 8에 기록한다.
채널 수가 어긋나면 명시적 `ValueError`를 내는 런타임 검사도 넣었다.

부작용: 정책이 "N초 지나면 포기하는 동작"을 배울 수 있다. 그런데 **포기 후
재접근이 바로 원하는 복구 행동**이고, 포기 궤적은 전부 score 0.0 구간에 있다.
추론 시 `Quality: 5`, `Mistake: false`로 조건을 걸면 그쪽으로 가지 않는다.

### 4.7 prefix pooled read 구현 노트

⚠️ **2026-09-23 개정: 차원이 320 → 960으로 바뀌었다.** 아래는 개정 후 기준이고,
이유는 학습 시 OOM이다.

#### 왜 바뀌었나

초기 구현은 prefix를 **두 번** 계산했다. `super().forward()`가 flow matching을
위해 VLM을 한 번 돌리고, 헤드를 위해 `encode_prefix()`가 또 한 번 돌리는 구조다.
두 activation이 backward까지 살아 있어야 하므로 메모리가 거의 두 배가 되고,
**배치 90 / H200에서 stage 4가 step 0에 OOM으로 죽는다**(137GB/139GB 사용).
stage 1은 헤드가 꺼져 있어 두 번째 경로를 안 타므로 문제가 드러나지 않았다.

해결은 **SmolVLA가 이미 계산하고 버리는 prefix 출력을 받아 쓰는 것**이다.
`VLAFlowMatching.forward`는 결과를 `(_, suffix_out)`로 해체하며 prefix hidden
states를 그냥 버린다. 후킹으로 그것을 가져오면 추가 연산도 추가 메모리도 없다.

#### 왜 `value_states`가 아니라 hidden states인가

원래 방식(KV 캐시의 `value_states`)은 **학습 경로에서 불가능하다.** 그 텐서는
`use_cache=True`일 때만 캐시에 저장되는데 학습 forward는 `use_cache=False`로
돌기 때문에 애초에 남지 않는다. 플래그를 바꿔 보는 시도는 두 번 다 막혔다:

| 시도 | 결과 |
|---|---|
| `fill_kv_cache=True` 강제 | 모든 레이어가 self-attn 경로로 가서 expert에 VLM 폭이 들어감 (`4500x720 and 320x320`) |
| `use_cache=True, fill_kv_cache=False` | 채운 적 없는 캐시를 읽으려 함 (`KeyError: 0`) |

두 플래그는 독립 스위치가 아니라 `VLMWithExpert.forward`의 **레이어 라우팅
조건**이다(`fill_kv_cache`가 조건의 첫 항). 그래서 플래그를 건드리지 않고
출력만 받는 방식으로 갔다.

#### 차원

`text_config.hidden_size = 960`. 이전의 320은
`num_key_value_heads(5) × head_dim(64)`였다 — grouped-query attention이라
query head 15개가 KV head 5개를 3:1로 공유해서 정확히 1/3이었다.
**카메라 3대와 3배가 우연히 일치하지만 무관하다.** 세 카메라는 원래부터
prefix 시퀀스에 나란히 들어가 있고, 바뀐 것은 "시퀀스를 어떻게 자르느냐"가
아니라 "각 위치를 무엇으로 표현하느냐"다.

hidden states 쪽이 정보량이 많고(attention + MLP + residual + layernorm을 모두
거친 최종 표현, value states는 그 중간 재료), 헤드 파라미터는 13만 → 39만으로
늘지만 403M 중 0.06%라 무시할 수준이다.

#### 학습과 추론이 같은 것을 본다

`encode_prefix()`(추론)도 hidden states를 쓰도록 통일했다. 추론 경로는
`read_state()`가 `select_action` 없이 30Hz로 단독 호출되므로 공유할 forward가
없어 재계산이 맞고, 그대로 두었다. **두 경로가 다른 특징을 보면 rollout에서
헤드가 무의미해지므로** 폭과 텐서 종류를 일치시키는 것이 핵심이다.

`_prefix_feature_dim()`이 config에서 유도하므로 하드코딩은 아니다.

#### 풀링

패딩 위치를 제외하고 풀링한다. prefix가 고정 길이로 우측 패딩되므로, 단순 평균은
짧은 프롬프트를 더 희석시켜 헤드가 프롬프트 길이에 민감해진다.

학습 경로에서는 캐시가 prefix와 suffix 위치를 모두 포함하므로, prefix 자신의
padding mask 길이로 잘라낸 뒤 풀링한다. suffix까지 평균내면 action expert의
상태가 "관측을 설명해야 할 특징"에 섞인다.

**헤드는 KI(Knowledge Insulation)의 역할도 한다.** pi0.6/0.7은 백본에 FAST 토큰
CE loss를 주고 action expert 그래디언트를 stop-gradient로 차단한다. SmolVLA에는
KI가 없어 flow matching 그래디언트가 백본을 직접 때린다. subtask/value CE 헤드가
그 안정적인 discrete signal을 대신 준다.

## 5. 플래너 / 태스크 매니저

### 5.1 규칙 기반인 이유

플래너가 하는 일을 데이터로 확인한 결과 **97% 결정론적**이다.
실패 없는 에피소드 217개에 대해 규칙 테이블이 **216개(99.5%)** 를 재현한다.

```
   68회 ✓  approach_pick → pick → move → place
   51회 ✓  approach_flip → flip → approach_pick → pick → move → place
   41회 ✓  move → place
   30회 ✓  approach_pick → pick
   26회 ✓  approach_flip → flip → approach_pick → pick
    1회 ✗  (두 부품을 연속 키팅한 에피소드 — 바깥 루프 부재이지 규칙 오류 아님)
```

**어려운 부분은 계획이 아니라 상태 추정이다.** 학습된 플래너는 97% 결정론적인
문제를 어렵게 푸는 것이다. 인터페이스는 VLM으로 교체 가능하게 두고 내부는 테이블.

### 5.2 복구 경로

```python
_RECOVERY = {FLIP: APPROACH_FLIP, PICK: APPROACH_PICK,
             MOVE: APPROACH_PICK, PLACE: APPROACH_PICK}
```

실패한 조작은 **중단된 지점에서 재개하지 않고 재접근으로 되돌린다.**
92건의 복구 사례 전부가 그렇게 했다.

`place` 실패 37건 중 **36건이 `approach_pick`으로** 이어진다 — 다시 집어서 재배치.

### 5.3 매니저 — 세 개의 시계

| 주기 | 담당 | 수단 |
|---|---|---|
| 30Hz | 행동 | action expert |
| 30Hz | 정체·이상 조기 경보 | **VLA 내부 `V_subtask`** (이미 forward에 포함, 저렴) |
| ~0.3Hz | 상태 확정 판정 | **인식기** (별도 모델, 풀 해상도) |

`place`에서 이 분리가 중요하다. value 헤드는 "이게 잘 안 되고 있다"를 일찍
연속적으로 말할 수 있지만, **"저 부품이 리브에 걸쳐 있다"는 인식기만 말할 수 있고
그게 재시도를 트리거하는 판정이다.** 빠른 신호만으로 게이트하면 AUC 0.98짜리
판정을 노이즈로 바꾸는 셈이다.

안전 장치:
- 재시도 상한 (서브태스크별 3회, 전체 6회)
- **히스테리시스** — 같은 판정이 2회 연속이어야 행동 (단일 노이즈 프레임 방지)
- 기권 → `NEEDS_OPERATOR` 정지
- 정체 감지 — value가 바닥(-0.95)에 6초 이상

검증한 시나리오 8종: 계획 생성, 거부 상태(`unknown_pose`/`abstain`/`empty`),
재계획, 정상 흐름, 실패 루프, 재시도 상한, 기권, 정체 감지 — 전부 통과.


두 스크립트는 **짝**이다. 하이퍼파라미터가 동일해야 비교가 유효하므로
한쪽을 바꾸면 다른 쪽도 바꾼다. 의도적 차이는 GPU 세트와 정책 지정뿐.

### 7.4 하이퍼파라미터 — 점검 후 수정한 것

| 항목 | 이전 | 현재 | 이유 |
|---|---|---|---|
| `scheduler_decay_steps` | 200000 | **`${TOTAL_STEP}`** | steps보다 크면 LeRobot이 자동 스케일하며 **warmup까지 절반으로** 줄임 |
| `TOTAL_STEP` | 100000 | **50000** | 유효배치 360 기준 127 epoch → 63 epoch. 292 에피소드에 127은 과적합 |
| `SCHED_WARMUP` | 미지정 | **1000 명시** | 자동 스케일에 휘둘리지 않도록 |
| `BEST_LOSS_WARMUP` | 20000 | 5000 | steps 축소에 맞춤 |

유지한 것:
- `optimizer_weight_decay=1e-4` — SmolVLA 기본 1e-10, pi0 1e-2의 중간.
  292 에피소드 단일 셀 데이터라 정규화 필요.
- `value_bins=201` — 201개 **전부 사용**, 최빈 bin 9.1%. 포화 없음.
- `subtask` 7-class — 최빈 23.3%로 균형적, 가중치 불필요.
- aux loss 합 1.37 vs flow loss ~2.4 — 주객전도 아님.

⚠️ `value_episode`는 `observation.time_left`에서 나오므로 **녹화된 에피소드 길이
기준**이다. 정책이 더 빠르거나 느리면 의미가 달라진다. 학습에는 문제없지만
추론 시 절대적 진척도로 해석하면 안 된다. 실패 탐지는 `V_subtask` 담당.

## 8. 현재 상태 — 무엇이 되고 무엇이 안 되는가

### ✅ 완성

| 요소 | 검증 |
|---|---|
| 인식기 | mat 94.5% / tray AUC 0.966, 플라시보 마진 통과 |
| 플래너·매니저 | 시연과 99.5% 일치, 8개 시나리오 통과 |
| 데이터 계층 | 대조 테스트 3종 PASS |
| MVLA 1~4단계 | 헤드 gradient 8/8, heads OFF 시 SmolVLA와 동일 손실 |

### ❌ 미구현

**5단계 subgoal 이미지 — 설정만 있고 실체가 없다**

`use_subgoal_images` 등 6개 파라미터는 선언돼 있지만 실제로 쓰는 코드가
`processor_mvla.py`의 `has_subgoal` 플래그 하나뿐이다. 없는 것:
- 미래 프레임 샘플링 (0~2초, 세그먼트 끝 40%)
- prefix에 subgoal 이미지 토큰 주입
- 어댑터가 `has_subgoal=True`를 넘기는 경로

⚠️ **`STAGE=5`로 실행하면 플래그는 받지만 아무 일도 일어나지 않고 조용히 4단계와 같아진다.**

**7단계 advantage — 더 나쁘다**

`adapter.py`가 **항상 `positive`**를 넣는다. RECAP의 핵심은 value function으로
advantage를 계산해 좋은/나쁜 데이터를 구분하는 것인데, 전부 positive면 무의미하다.
필요한 것: 학습된 V로 advantage 추정, 태스크별 임계값 ε_ℓ(pi0.6은 30 퍼센타일),
rollout 데이터.

⚠️ **`STAGE=7`은 지금 쓰면 안 된다.**

**런타임 통합**

`planner/manager.py`는 동작하지만 **VLA와 연결되지 않았다.** 매니저가
`MVLAPolicy.select_action`을 호출하고 `read_state`로 value를 폴링하는 루프가 없다.
학습에는 무관하나 **실제 로봇 구동에는 필수**.

**평가 도구**

헤드 오프라인 평가 스크립트가 없다. 94건 실패 런에 대한 탐지 AUC·리드타임을
재려면 필요하다. 학습/검증 분할도 아직 안 나눴다(292개 전부 학습에 사용 중).

## 12. 개발 중 잡은 버그 — 같은 실수 방지

1. **플라시보 대조가 없었다면 98%짜리 가짜 결과를 보고했을 것.**
   배경 단서는 세션을 넘으면 역방향으로 작동한다(45.5%).

2. **블록 순서를 섞으면 세션 대조가 죽는다.** "5회 반복 평균"을 하면서
   시드마다 순서를 섞었더니 플라시보가 0.122 → 0.657로 부풀었다.
   연속 블록을 유지하고 블록 개수만 바꿔야 한다.

3. **Task B 1차 측정이 무효였다.** 런 종료 프레임은 팔이 3초 물러난 뒤라
   시야가 넓어 "플라시보" 영역에 대상 부품이 들어갔다.

4. **중립 프롬프트 1차 시도 실패.** task 0을 `prepare...for picking`으로 따로
   매핑해 누수가 남았다. 목표 기준 재분류로 해결.

5. **status 가중치가 67배 부족했다.** `(1,5,15)`로는 always-running 손실이
   0.27이라 헤드가 붕괴한다.

6. **`elapsed_subtask`를 state에 직접 붙이면 정규화가 깨진다.**
   통계가 8채널 기준이므로 9번째에서 broadcast 실패. 정규화 이후에 붙여야 한다.

7. **SmolVLA prefix-only 경로(추론)는 `fill_kv_cache=True`와만 동작한다.**
   반대로 **학습 경로에서는 그 플래그를 건드리면 안 된다** — `use_cache`/
   `fill_kv_cache`는 독립 스위치가 아니라 레이어 라우팅 조건이라, 강제하면
   expert에 VLM 폭이 들어가거나(`4500x720`) 빈 캐시를 읽는다(`KeyError: 0`).
   학습은 SmolVLA가 버리는 prefix hidden states를 후킹으로 받는다. §4.7 참고.

7b. **헤드를 위해 prefix를 다시 계산하면 배치 90에서 OOM이다.**
   activation이 두 벌 살아남아야 해서 메모리가 거의 두 배. stage 1은 헤드가
   꺼져 있어 안 드러나고 stage 4에서 step 0에 죽는다.

8. **`itertuples()`는 슬래시가 든 컬럼명을 속성으로 노출하지 못한다.**
   `videos/observation.images.wrist_front/file_index` 등은 인덱싱으로 접근.

9. **`or []`가 numpy 배열에 걸리면 ambiguous truth value 오류.**
   `np.atleast_1d()`로 정규화.
