# 2026-09-23 — MVLA 학습 스크립트 실행 불가 문제 해결

`train_xarm7_mvla.sh`가 실행되지 않던 문제를 추적해 수정했습니다. 표면적으로는 하나의 에러였지만, 고칠 때마다 다음 에러가 드러나는 구조였고 총 다섯 가지 원인이 있었습니다. 커밋은 `e7f8d548`.

## 1. `mvla` 정책이 등록되지 않음

```
lerobot-train: error: argument --policy.type: invalid choice: 'mvla'
```

`MVLAConfig`는 `@PreTrainedConfig.register_subclass("mvla")` 데코레이터로 자기 자신을 등록하지만, **그 모듈을 아무도 import하지 않아 등록 코드가 실행되지 않았습니다.** CLI 파서는 이 레지스트리에서 선택지를 만들기 때문에 `mvla`가 목록에 없었습니다.

`factory.py`는 이미 `mvla` 분기를 갖고 있었으므로(`get_policy_class`, `make_policy_config` 모두) 빠진 건 import 한 줄뿐이었습니다.

**수정**: `src/lerobot/policies/__init__.py`에 다른 정책들과 같은 방식으로 config import 추가.

> 참고: `sarm`은 `factory.py`의 최상위 import를 통해 우연히 등록되고 있었습니다. 정책마다 등록 경로가 다른 건 기존 코드의 일관성 문제입니다.

## 2. `data/` 패키지 전체가 존재하지 않음 — 가장 큰 작업

```
ModuleNotFoundError: No module named 'lerobot.policies.mvla.data'
```

`datasets/factory.py`, `planner/rules.py`, `recognizer/dataset.py`, `tests/test_against_dataset.py`가 모두 이 패키지를 import하고 있었지만 **어느 커밋에도 존재한 적이 없었습니다.** 세 모듈을 새로 작성했습니다.

| 모듈 | 역할 |
|---|---|
| `data/segments.py` | subtask run 경계와 실패 판정 — 모든 정의의 단일 출처 |
| `data/derive.py` | 프레임별 head 타깃, 중립 프롬프트 |
| `data/adapter.py` | 데이터셋 래퍼 (프롬프트 조립 + 타깃 부착) |

### 규약을 추측하지 않고 역산한 과정

`configuration_mvla.py` 주석에 status 분포가 `283194 running / 1274 success / 94 failure`로 적혀 있었습니다. 이 숫자가 의도된 정의를 복원할 유일한 단서였고, 두 가지를 확정했습니다.

**run 경계 = 프레임별 `subtask_index` 변화점**

에피소드 메타데이터의 `subtask_start_frames`를 쓰면 1379개, 프레임 컬럼의 변화점을 쓰면 1368개가 나옵니다. 메타데이터는 프레임 컬럼이 병합하는 인접 동일 subtask run을 분리합니다. `1274 + 94 = 1368`이므로 **프레임 컬럼이 정답**입니다.

**실패 = run 내 `subtask_score`가 0에 닿으면 (`min == 0`)**

| 판정 기준 | 실패 수 |
|---|---|
| 마지막 프레임 `score == 0` | 87 |
| `score < 0.5` | 105 |
| **`min(score) == 0`** | **94** ✓ |

편집자가 "문제가 생긴 순간"을 표시하는데 그게 항상 run의 마지막 프레임은 아닙니다. 마지막 프레임만 보면 94개 중 7개를 놓칩니다. 0과 1 사이의 중간 점수는 실패가 아니라 품질이고, 프롬프트로 들어갑니다.

두 규약을 적용한 결과 `283194 / 1274 / 94`가 **정확히** 재현됩니다.

## 3. `rename_map`이 정책 feature에 적용되지 않음

```
ValueError: All image features are missing from the batch.
```

`make_policy`가 `rename_map`을 인자로 받아놓고 **검증을 건너뛰는 데에만 쓰고, 실제 feature 이름에는 적용하지 않았습니다.**

smolvla에서 드러나지 않았던 이유는 실행 경로가 다르기 때문입니다:

- `--policy.path=lerobot/smolvla_base` → 사전학습 config의 `input_features`(이미 `camera1/2/3`)를 상속 → 문제 없음
- `--policy.type=mvla` → `input_features`가 비어 있어 **데이터셋의 원래 카메라 이름**으로 채워짐 → 배치는 renamed 이름으로 도착 → 전부 불일치

**수정**: `factory.py`에서 데이터셋으로부터 feature를 유도한 직후 rename을 적용. smolvla 경로가 영향받지 않음을 실제로 확인했습니다(`input_features`가 전후 동일).

이건 mvla만의 문제가 아니라 **`--policy.type` + `rename_map` 조합을 쓰는 모든 정책에 해당하는 공용 코드 버그**입니다.

## 4. 보조 head가 gradient를 전혀 받지 못함 — 가장 중요

가장 늦게 발견했고, 가장 위험했던 문제입니다.

### 무엇이 잘못됐나

수정 3까지 끝낸 뒤 학습이 정상적으로 돌기 시작했고, loss가 1.769 → 0.772로 떨어지는 것을 보고 정상이라고 판단했습니다. **이 판단은 틀렸습니다.**

wandb에 기록된 메트릭을 확인해보니 다음이 전부였습니다:

```
train/loss, train/grad_norm, train/lr,
train/losses_after_forward, train/losses_after_in_ep_bound, train/losses_after_rm_padding
```

뒤의 세 개는 **SmolVLA 자신의 키**입니다. `loss_subtask`, `loss_value_subtask`, `loss_value_episode`, `loss_status`는 하나도 없었습니다. 즉 **4개 보조 head 전부가 gradient를 받지 못한 채로 돌고 있었습니다.**

### 원인

전처리 파이프라인의 `batch_to_transition`이 배치를 `EnvTransition`으로 변환하면서 **`observation.` 접두사가 붙은 키와 고정된 allowlist(`task`, `index`, `episode_index`, `*_is_pad`)만 남기고 나머지를 조용히 버립니다.**

어댑터가 `subtask_index`, `value_subtask` 같은 평범한 이름으로 내보내고 있었으므로 정책에 도달하기 전에 사라졌습니다. `MVLAPolicy.forward`의 가드가 `any(k in batch for k in TARGET_KEYS)`라서, 타깃이 없으면 **조용히 보조 손실을 건너뜁니다.** 에러도, 경고도 없습니다.

### 수정

타깃 키에 `observation.` 접두사를 붙이고, 키 정의를 `modeling_mvla.py` 한 곳에 두고 어댑터가 import하도록 했습니다. 왜 접두사가 필수인지는 코드 주석에 남겼습니다.

```
observation.subtask_index, observation.value_subtask,
observation.value_episode, observation.status, observation.elapsed_subtask
```

### 검증

실제 데이터셋 → 어댑터 → DataLoader → 전체 전처리 파이프라인을 통과시킨 배치에서 5개 키가 모두 생존하고, 그 타깃으로 4개 head 손실이 전부 산출되는 것을 확인했습니다.

### 교훈

**loss가 떨어진다는 것은 학습이 의도대로 되고 있다는 증거가 아닙니다.** 여기서는 SmolVLA의 flow-matching 손실만으로도 곡선이 정상으로 보였습니다. 보조 목적함수를 추가했다면 그 손실 항이 실제로 로그에 찍히는지를 따로 확인해야 합니다.

## 판단이 필요했던 부분 — 프롬프트 leak 기준 완화

`tests/test_against_dataset.py`의 `MAX_NEUTRAL_LEAK`이 0.60이었는데 실측값이 0.616으로 살짝 넘었습니다.

| 프롬프트 | leak |
|---|---|
| 원본(방법을 명시) | 0.997 |
| 중립, 두 goal 구분 | 0.616 |
| 절대 하한(전부 한 문장) | 0.582 |

leak은 "프롬프트만 보고 flip이 필요한지 맞히는 최선의 규칙"의 정확도입니다. 하한이 0.5가 아니라 0.582인 이유는 292개 중 122개만 flip이 필요해서, "전부 flip 없음"이라고 답하는 것만으로 이미 58.2%이기 때문입니다.

남은 0.616은 **어휘 문제가 아니라 구조적**입니다. "kit"과 "pick" 두 goal의 flip 빈도가 실제로 다릅니다(36.8% vs 56.9%). 0.60 아래로 내리려면 두 goal을 한 문장으로 합쳐야 하는데, 그러면 planner가 의존하는 goal 구분이 사라집니다.

**사용자 확인 후 기준을 0.62로 완화**하고 위 근거를 주석에 남겼습니다. 원본 프롬프트(0.997)가 다시 새어 들어오면 여전히 실패합니다.

## 실행 방법

```bash
# STAGE는 환경변수, 기본값 4
./train_xarm7_mvla.sh              # stage 4
STAGE=1 ./train_xarm7_mvla.sh      # stage 1
```

| STAGE | 내용 |
|---|---|
| 1 | baseline — head 전부 off, 프롬프트 원문. **SmolVLA와 일치해야 함** |
| 2 | + subtask 프롬프트/head |
| 3 | + quality/speed/mistake 메타데이터, 중립 프롬프트 |
| 4 | + value & status head, elapsed-in-subtask (기본값) |
| 5 | + subgoal 이미지 |
| 7 | + advantage conditioning (value function 필요) |

stage는 누적이며, 각 추가 항목의 기여를 분리해 측정하기 위한 설계입니다. stage 1은 단순한 시작점이 아니라 **검증 단계**입니다 — 모든 head를 끄면 데이터 래퍼가 적용되지 않으므로 SmolVLA와 같은 결과가 나와야 하고, 그렇지 않다면 데이터 레이어나 정책 서브클래싱에 버그가 있다는 뜻입니다.

GPU는 스크립트에 분리되어 있어(mvla 0-3, smolvla 4-7) 동시 실행이 가능하며, 같은 조건에서 나란히 돌리는 편이 비교에 유리합니다.

출력 디렉토리가 이미 있으면 `FileExistsError`로 즉시 종료되므로 재실행 전 삭제가 필요합니다.

## 남은 확인 사항

1. **stage 1의 loss 곡선이 SmolVLA와 겹치는지** — 데이터 셔플 seed 차이로 완전히 동일하지는 않지만, 눈에 띄게 갈라지면 데이터 레이어나 서브클래싱 문제 신호
2. **stage 2 이상에서 wandb에 `loss_subtask` / `loss_value_*` / `loss_status`가 찍히는지** — 위 4번 문제의 재발 여부를 직접 확인하는 유일한 방법. 콘솔 한 줄에는 나오지 않고 wandb에만 기록됨
