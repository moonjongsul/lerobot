## 2. 평가 도구 — `python -m lerobot.policies.mvla.eval_heads_cli`

```bash
python -m lerobot.policies.mvla.eval_heads_cli \
  --checkpoint checkpoints/outputs/<job>/checkpoints/050000 \
  --modes train,oracle,blind --closed-loop --actions oracle,blind
# SmolVLA: --actions recorded,neutral
```

결과는 `<checkpoint>/eval/<name>.json`. 풀 평가 1회 ≈ 15~20분(GPU 1장).

| 평가 | 무엇을 재나 |
|---|---|
| 헤드 개루프 `train` | 학습 프롬프트 그대로 (옛 wandb `val/*` 재현) |
| `oracle` | 추론 프롬프트 + 정답 subtask, `Mistake: false` 고정 |
| `blind` | `Task: <중립 문장>.`만 — 프롬프트에서 베낄 게 없음 |
| `--closed-loop` | 런타임 재현: 헤드 예측이 자기 프롬프트 subtask와 경과시간을 결정 |
| `--actions` | held-out 액션 청크 오차. SmolVLA에도 돌아가는 유일한 공통 지표 |

### 고친 것

- **`lead_s` / `lead_detected` 지표 폐기.** value 타깃은 성공 런도 -1에서
  출발하므로 모든 런이 첫 프레임에 임계 아래 → 실패 런 평균 길이를 재고 있었다
  (`lead_detected`가 항상 1). 대신 매니저의 실제 정체 규칙을 시뮬레이션:
  `stall_detect`, `stall_false_alarm`, `stall_lead_s`.
- `failure_auc_value_mean` 추가(런 평균값 점수). 최저값 점수는 런 시작부에 좌우된다.
- subtask 혼동행렬.
- **학습 중 val은 이제 `blind` 프롬프트**(`lerobot_train.py`). 다음 런부터
  wandb `val/*` 숫자가 이전 런과 직접 비교되지 않는다.
- `MVLADatasetWrapper(prompt_mode=...)` 추가 (`train`이 기본, 학습 동작 불변).

|---|---|---|---|
| 8k | 0.938 / 0.906 | 0.918 / 0.890 | 0.814 |
| 16k | 0.932 / 0.907 | 0.883 / 0.819 | 0.696 |
| 24k | 0.917 / 0.900 | 0.890 / 0.858 | 0.648 |
| 50k | 0.911 / 0.902 | 0.862 / 0.841 | 0.550 |

학습 프롬프트에는 정답 subtask와 `Mistake:`(런 실패 플래그)가 들어가고 중립 문장이면
48토큰 안에 전부 들어간다. 그래도 차이는 1~3점 — **헤드는 주로 이미지를 읽는다.**
처음에 누수가 지표를 대부분 만들었을 거라고 봤는데 틀렸다.

### 폐루프 subtask 추적 — 동작한다

| step | 헤드 프롬프트 | 추적 정확도 | 경계 놓침 | 지연 중앙/p90 | 헛넘김 |
|---|---|---|---|---|---|
| 8k | self | 0.901 | 1.5% | 0.4 / 1.6 s | 67 |
| 8k | blind | 0.909 | 1.0% | 0.0 / 1.3 s | 112 |
| 50k | self | 0.902 | 1.5% | 0.2 / 1.4 s | 104 |
| 50k | blind | 0.903 | 1.0% | 0.1 / 1.4 s | 120 |

경계 201개. **멈춘 에피소드 0개** — 헤드가 자기 subtask를 베껴 안 넘어가는 문제는
없었다. 헛넘김은 평가에서는 어느 subtask로든 넘어가게 해서 센 것이고, 런타임은
plan의 다음 subtask로만 전진하므로 대부분 걸러진다. 런타임 기본값은 `self`.

### 정체 경보 — 매니저 규칙이 거의 안 걸린다 ⚠️

| step | detect@6s | detect@3s | 오경보@3s |
|---|---|---|---|
| 8k | 0.00 | 0.25 | 0.016 |
| 50k | 0.00 | 0.25 | 0.024 |

(blind 기준.) value에 정보는 있다(AUC 0.84~0.89). 하지만 실패 런에서 예측값이
-0.95 아래에 6초 머무는 일이 거의 없다. **`ManagerConfig.stall_value`/`stall_seconds`
재보정 필요.** 그 전까지 실기에서 실패 판단은 사람이 한다.

### 액션 — 개루프 오차로는 두 정책이 구분되지 않는다

| | 8k | 24k | 50k |
|---|---|---|---|
| MVLA oracle | 0.477 | 0.468 | 0.464 |
| MVLA blind | 0.479 | 0.468 | 0.464 |
| SmolVLA recorded | 0.464 | 0.462 | 0.466 |
| SmolVLA neutral | 0.474 | 0.475 | 0.479 |

(정규화 공간 MSE, 청크 50스텝, stride 30.) 차이 1~3%. 8k→50k도 거의 평탄 —
개루프 액션 오차로는 과적합도 개선도 안 보인다. SmolVLA에 중립 프롬프트를 주면
약간(+2.8%) 나빠진다. **비교는 rollout으로만 가능하다.**

### 체크포인트 선택

rollout 1순위는 **50k** (액션 오차 최저, 추적 정확도 동일). 헤드 지표는 8k가
좋으므로 여력이 되면 8k 또는 16k를 두 번째 조건으로.

## 4. rollout 코드 — `ros_inference/`

자세한 건 `ros_inference/README.md`. 요점:

- ROS 없는 코어(관측 변환, 안전 제한, 시간 기준 청크 실행, MVLA subtask 추적,
  정책 실행) + 얇은 rclpy 노드. 코어는 이 PC에서 검증:
  단위 테스트 13개, 녹화 에피소드 replay(`python -m ros_inference.replay`).
- 관측 = `/xarm/eef_twist` 6 + 그리퍼 위치 + 정규화 effort (녹화와 동일).
  액션 → `/xarm/vc_set_cartesian_velocity` (mm/s로 변환, duration 0.2s 워치독),
  그리퍼 Float32 0/1.
- `/data_collection/rollout_action`(TeleopAction)을 퍼블리시하고 레코더 START/SAVE
  → rollout이 데모와 같은 스키마로 쌓인다.
- MVLA 시작 상태: 그리퍼 effort로 파지 판단, 아니면 헤드가 approach_flip/pick 선택
  (인식기 연동 전 대체). replay ep33에서 flip 필요를 맞힘, 추적 91%.

### 실기 전 확인할 가정

1. 선속도 단위: 녹화는 **m/s**(action ±0.25), `TeleopAction.msg` 주석은 mm/s라고
   한다. m/s로 보고 서비스엔 ×1000. 첫 실행은 `--speed-scale 0.1`.
2. `is_tool_coord`는 녹화되지 않았다 → 베이스 좌표 가정.
3. teleop 노드 코드가 m.ax 저장소에 없어 서비스 이름·타입은 xarm_ros2 표준 가정.
4. 작업공간 z 하한은 셀에서 실측.
5. `stats.json`의 q01/q99는 에피소드별 값의 평균이라 전체 분포보다 훨씬 좁다
   (eef x: q01 -0.04 vs 실제 0.1% -0.30). 작업공간 박스는 원본 프레임에서 계산했다.

## 5. 메인 prompt 작업 종료 판단

`python -m lerobot.policies.mvla.eval_termination --checkpoint <ckpt>` (val 58개)

| 규칙 (마지막 subtask 안에서, 3회 연속) | 8k 발동 / p10 | 50k 발동 / p10 |
|---|---|---|
| value_episode ≥ -0.05 | 0.95 / -2.0s | 0.90 / -2.3s |
| value_subtask ≥ -0.05 **또는** value_episode ≥ -0.05 (채택) | 0.95 / -2.0s | 0.90 / -2.6s |
| 같은 OR, value_subtask ≥ -0.10 | 0.95 / -2.0s | 0.97 / **-7.1s** |

중간 오발동 0%, 발동 중앙값은 실제 끝 1.2초 전(끝에는 놓고 물러나는 ~3초 포함).

**prompt 의존성은 없다.** 같은 프레임에 목표 문장만 pick↔kit로 바꿔도 value_episode가
그대로(kit 에피소드의 pick 끝 -0.383/-0.385, pick 에피소드 끝 -0.006/-0.006).
헤드는 장면으로 끝을 판단한다 — 과제 유형별로 녹화 세션이 달라 val에선 맞았을 뿐.
그래서 런타임은 **plan(목표→subtask 순서)의 마지막 subtask 완료**를 작업 종료로 본다.

value_episode를 진짜 prompt 조건부로 만들려면 학습 데이터에 같은 장면·다른 목표가
있어야 한다: kit 에피소드를 pick 끝에서 잘라 pick 목표 에피소드로 재라벨(hindsight
goal relabeling)하면 value_episode 타깃이 목표에 따라 달라진다.

## 6. 인식기 재학습 (train 234개만, val 58개 held-out)

```bash
python -m lerobot.policies.mvla.recognizer.train \
  --dataset ~/.cache/huggingface/lerobot/moonjongsul/xarm7-kitting-260923 \
  --out checkpoints/outputs/mvla_recognizer_split_260923 --split split_260923.json
```

이 PC에는 학습된 인식기가 없었다(설계 문서의 `outputs/mvla_recognizer/`는 다른 환경).
재학습에 필요했던 수정: `--split` 옵션과 held-out 평가(`holdout_evaluate`) 추가,
`dataset._release_frames`가 캐시 함수에 list를 넘겨 즉시 죽던 버그 수정, scikit-learn 설치.

| | 설계 문서 (292개 CV) | train CV (234개) | **held-out val (58개)** |
|---|---|---|---|
| mat 3-way 정확도 / AUC | 94.5% / 0.991 | 94.2% / 0.987 | 96.6% / 0.999 |
| mat 플라시보 마진 | +0.181 | +0.187 | **+0.071 (SUSPECT)** |
| mat 매트 위 2-class AUC / 마진 | 0.983 / +0.428 | 0.971 / +0.327 | 0.999 / +0.189 |
| tray 정확도 / AUC | 95.7% / 0.966 | 95.6% / 0.953 | 98.0% / 0.987 |
| tray 플라시보 마진 | +0.255 | +0.312 | +0.185 |

- 설계 문서 수치는 재현된다.
- held-out mat 3-way 마진이 낮은 건 `empty` 클래스 때문(물체가 그리퍼에 있으면 팔 위치가
  어느 크롭에서든 보임). 매트 위 2-class로 한정하면 +0.189로 통과. flip 판단(target vs
  flipped)에 쓰는 건 이 2-class 쪽이다.
- tray held-out은 bad 7건뿐이라 넓게 봐야 한다. 임계 0.5에서 6/7 탐지, 오경보 0.
  train CV에서 설계 권장 임계 0.3은 recall 0.83 / precision 0.77 (설계 0.92 / 0.76).
- tray bad 샘플은 36런(108프레임). 설계 문서는 37 — 마지막 프레임 점수로 라벨을
  정하는 탓에 `min==0` 규약과 1건 차이 나는 것으로 보인다. 확인 필요.

## 7. 인식기 런타임 연결

- **런타임 경로 버그 수정**: `StateRecognizer.__call__`이 크롭 없이 전체 프레임을
  인코딩하고 있었다(학습은 mat 실루엣 크롭 / tray 창 크롭, RGB). 매니저 경로가 한 번도
  실행된 적 없어 드러나지 않았다. 수정 후 val 프레임에서 held-out 결과 재현
  (mat 96.0%, tray 96.7%, 기권 0).
- `ros_inference/recognition.py` + tracker: 시작 상태(mat), flip 검증(mat), place 검증(tray).
  캡처 시각은 학습 샘플과 같게(approach +3/12/21, 릴리스 +8/18/28프레임).
- `TaskManager.verification_failed()` 추가 — flip은 먼저 넘어가고 판정이 뒤집는다.
- **플래너 복구 규칙 수정** (`rules.replan_after_failure`): place/move 실패(와 트레이
  재시도 중 pick 실패) → `approach_pick → pick → place`. 데이터에서 place 실패 뒤 31건
  전부 move 없이 트레이에서 다시 집었다. 이전 규칙(move 포함)이면 runtime이 오지 않을
  move를 기다리며 멈춘다(ep280에서 실제로 멈춤).
- tray 임계 설정 가능(`recognizer.tray_bad_threshold`, 기본 0.3).

replay 결과는 `ros_inference/README.md` 표 참고. 요약: 정상 4개·place 실패 3개가 녹화와
같은 흐름으로 완료. ep249는 성공한 두 번째 place를 `bad`로 오판(임계 0.3의 오경보).
